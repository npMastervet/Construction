# ประเมินงานขั้นถัดไป: ยืนยันโมเดลธุรกิจก่อนสร้างโมดูล

สถานะล่าสุด: ผู้ใช้มอบหมายให้กำหนดตามความเหมาะสมแล้ว จึงปิดค่าเริ่มต้นสำหรับเริ่มพัฒนาใน [ชุดข้อกำหนดระยะ 0](phase-0/README.md) เอกสารด้านล่างเก็บไว้เป็นบริบทการประเมิน; ยังต้องตรวจงานจริงก่อน UAT แต่ไม่ต้องรอการตัดสินใจเดิมซ้ำก่อนเริ่มระยะข้อมูลและสิทธิ์

## ข้อสรุป

ขั้นถัดไปคือ **ระยะ 0 — ยืนยันแบบจำลองธุรกิจ** ใช้เวลาโดยประมาณ 4–6 วันทำงานสำหรับนักพัฒนา 1 คน ร่วมกับผู้ใช้งานธุรกิจในการตอบข้อกำหนดสำคัญ

การตัดสินใจด้านล่างกำหนดโครงฐานข้อมูลและสิทธิ์ของทุกโมดูล หากย้อนมาแก้ภายหลังจะต้องแก้ migration, API, รายงาน และข้อมูลที่บันทึกไปแล้วพร้อมกัน ปัจจุบันกำหนดรายละเอียดแล้วในชุดระยะ 0

```text
ตัวอย่างงานจริง + กติกาธุรกิจ
              |
              v
ERD + สิทธิ์ราย action + สูตรเงิน
              |
              v
API contract + ชุดตัวอย่างตรวจยอด
              |
              v
ระยะ 2: Organization / Project / Supplier / Access
              |
              v
ระยะ 3–5: BOQ -> ค่าใช้จ่าย/จ่ายเงิน -> รายงาน
```

## สิ่งที่ต้องตัดสินใจและเหตุผล

| เรื่อง | ค่าเริ่มต้นที่แนะนำ | เหตุผลและผลต่อระบบ |
|---|---|---|
| เจ้าของข้อมูล | หนึ่งกิจการ มีหลายผู้ใช้ และข้อมูลถูกครอบด้วย `Organization` | ต้องมี `OrganizationMember` และ `ProjectMember`; `UserCompany` enum เดิมต้องเลิกใช้ก่อนนำฐานจริงขึ้น |
| สิทธิ์ | เจ้าขององค์กร, บัญชี, ผู้จัดการโครงการ, ผู้บันทึกหน้างาน, ผู้ดูข้อมูล | กำหนดว่าใครเห็นต้นทุน/กำไร ใคร post ค่าใช้จ่าย ใครอนุมัติ BOQ และใครบันทึกการจ่ายเงิน |
| BOQ | BOQ เป็น “ประมาณต้นทุน”; ราคาขายและมูลค่าสัญญาเก็บแยก | ป้องกันการนำมูลค่าเสนอขายมาเปรียบเทียบต้นทุนจริงผิดความหมาย; BOQ ที่อนุมัติต้องสร้าง baseline และ revision |
| ค่าใช้จ่าย | หนึ่งเอกสารต่อหนึ่งโครงการ, หนึ่ง VAT mode/rate, มีรายการย่อย | ทำให้การ post, ยอด VAT และรายงานตรวจสอบได้; เอกสารหนึ่งใบแบ่งหลายโครงการเป็นขอบเขตเพิ่ม |
| การจ่าย | เก็บ `Payment` แยกจาก `ActualCost` | รองรับจ่ายบางส่วน/หลายครั้ง และคำนวณยอดค้างจากประวัติจริง ไม่พึ่ง status อย่างเดียว |
| การแก้ข้อมูล | Draft แก้ได้; posted document ใช้ void/replacement; payment ใช้ reverse | รักษาประวัติและไม่ทำให้ยอดในรายงานเปลี่ยนเงียบ ๆ |
| VAT/เงิน | THB, decimal arithmetic ฝั่ง server, rate ต่อเอกสาร | ต้องยืนยันวิธีปัดเศษและการนับ VAT เป็นทุนหรือภาษีแยกก่อนทำรายงาน |
| ไฟล์ใบเสร็จ | Private object storage, DB เก็บ metadata/reference | ไม่เก็บ data URL ใน record; ต้องเลือก storage provider ในระยะ implementation |
| ข้อมูลเดิม | สำรวจ localStorage และ Excel ก่อนสร้าง import | ยังไม่มีหลักฐานว่าไม่มีข้อมูลใช้งานจริง; ต้อง backup และกระทบยอดก่อนตัดสินใจไม่ย้าย |

## ผลส่งมอบของระยะ 0

1. ERD ฉบับอนุมัติ ครอบคลุม `Organization`, `OrganizationMember`, `Project`, `ProjectMember`, `Supplier`, `BoqVersion`, `BoqItem`, `ActualCost`, `ActualCostItem`, `Payment`, `FileAsset`, `AuditLog` และความสัมพันธ์กับ User
2. Permission matrix ราย action ไม่ใช่แค่ชื่อตำแหน่ง เช่น `project.create`, `project.read`, `boq.approve`, `cost.post`, `payment.write`, `financial.read`, `report.export`, `file.download`
3. State-transition table สำหรับ Project, BOQ, ActualCost และ Payment reversal พร้อมผู้มีสิทธิ์แต่ละ transition
4. Data dictionary กำหนดชนิดเงิน Decimal, วันที่, VAT mode/rate, หมวดต้นทุน, project status และข้อห้ามของข้อมูล
5. API contract ระดับแรกสำหรับ Organization/Member, Project, Supplier พร้อม request/response/error examples และ pagination/filter contract
6. ชุดตัวอย่างงานจริงที่ไม่ใช่ข้อมูลส่วนบุคคลเกินจำเป็น: อย่างน้อย 2 โครงการ, BOQ, ค่าใช้จ่าย, VAT และรายการจ่ายเงิน พร้อม expected totals
7. Test scenarios ด้านสิทธิ์และการคำนวณก่อนเริ่มเขียน schema

## ขอบเขตที่จะพัฒนาในระยะถัดจากระยะ 0

เมื่อผลส่งมอบข้างต้นผ่าน จึงเริ่ม **ระยะ 2 — ข้อมูลและสิทธิ์** ประมาณ 6–9 วันทำงาน:

- แทน `UserCompany` ด้วย Organization/สมาชิกองค์กร โดยมี migration ที่ปลอดภัยสำหรับฐานใหม่
- สร้าง permission middleware ที่ตรวจ account active, membership active, action permission และ project scope จากฐานข้อมูลทุก request
- สร้าง modules สำหรับ Organizations, Users/Members, Projects และ Suppliers
- เพิ่ม audit event สำหรับสร้าง/แก้ไข/เปลี่ยนสถานะ/มอบหมายสมาชิก
- ทำ Client pages แบบ lazy-loaded สำหรับรายการโครงการ, รายละเอียดโครงการพื้นฐาน, ผู้ขาย และการมอบหมายสมาชิก
- เพิ่ม integration tests ป้องกันอ่าน/แก้/ดาวน์โหลดข้อมูลข้ามองค์กรหรือโครงการ

ยังไม่รวม BOQ editor, Actual Cost, Payment, upload files หรือรายงาน เพราะต้องใช้ foundation ของ Organization/Project access ให้เสร็จก่อน

## เกณฑ์ผ่านก่อนเริ่ม BOQ

- ผู้ใช้ที่ไม่มี membership อ่านหรือเดา project ID ของอีกองค์กรไม่ได้จาก API
- ผู้ใช้ที่ถูกถอนออกจากโครงการทำ request ต่อไม่ได้
- ผู้ดูข้อมูลไม่ได้รับฟิลด์ต้นทุนหรือมูลค่าสัญญาจาก API ถ้าไม่มี `financial.read`
- สร้างและมอบหมายโครงการได้ พร้อม audit ที่ตรวจย้อนกลับได้
- Project และ Supplier ทุก record อยู่ภายใต้ Organization เสมอ
- migration, Prisma generate/validate, lint, typecheck, integration tests และ build ผ่าน

## ความเสี่ยงและสิ่งที่ไม่ควรเลื่อน

- ถ้ากิจการมีการแบ่งหลายทีม/บริษัท หรือให้บุคคลภายนอกเข้าดูโครงการ ต้องยืนยันก่อนออกแบบ `ProjectMember`; การเพิ่มหลังมีข้อมูลแล้วมีต้นทุนสูง
- หาก BOQ ในงานจริงเป็นใบเสนอขาย ไม่ใช่ประมาณต้นทุน ต้องแยก model ของ estimate/quotation ก่อนเขียน editor
- ถ้ามี VAT หลายอัตรา, retention, เงินมัดจำ, หัก ณ ที่จ่าย หรือหนึ่งบิลแบ่งหลายโครงการ ให้ขยาย model ก่อน migration แรกของค่าใช้จ่าย
- ภาพ/ไฟล์ใบเสร็จต้องเลือกพื้นที่เก็บแบบ private และกติกา retention ก่อนเปิด upload
- เลือก Google OAuth และฐาน MySQL จริงก่อน UAT; ปัจจุบันพื้นฐานทดสอบได้โดยไม่ตั้ง credentials แต่ login จริงยังทดสอบไม่ได้

## ข้อมูลที่ควรเตรียมเพื่อปิดระยะ 0

- BOQ งานจริงหนึ่งหรือสองโครงการที่ตัดข้อมูลส่วนบุคคลได้
- ใบเสร็จ/รายการค่าใช้จ่ายตัวอย่าง พร้อมคำตอบว่า VAT และการจ่ายบางส่วนต้องนับอย่างไร
- รายชื่อหน้าที่ของผู้ใช้จริง และขอบเขตข้อมูลที่แต่ละหน้าที่ควรเห็น
- ตัวอย่างรายงานที่ต้องการใช้ตัดสินใจ พร้อมนิยามของคำว่า “กำไร” และช่วงวันที่
- จำนวนผู้ใช้ จำนวนโครงการ และปริมาณไฟล์โดยประมาณ เพื่อเลือก database/storage/hosting ในระยะต่อไป
